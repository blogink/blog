如何在 Serv00 上部署卫戍协议同人游戏

发表于2026-10-18|更新于2026-10-18|经验记录
|总字数:3.1k|阅读时长:11分钟|浏览量:

不久前在 QQ 群中了解到这个非官方的同人项目，大致是复刻了游戏《明日方舟》中的一个限时开放的玩法。

这个项目基于 Node.js 运行，想起 Serv00 支持 Node.js 运行环境，遂尝试部署（这应该是我在 Serv00 上运行的第一个非 PHP 程序了）。

以下为免责声明，摘录自项目仓库介绍文档

附：本文提及该程序仅为案例分析、学习交流需要，与上述企业和项目原作及关联方无关。搭建完的实例也不建议公开宣传，也是对项目的保护。

上传文件

访问 Stronghold-Protocol 仓库的 Release，下载最新发行版（整合包），截止本文完稿时最新版为 0.3.0。为了加快速度，我下载了 lite 版本。

接下来，登入 Serv00 的控制面板（面板具体地址在注册时的邮箱可以找到），此处以新版控制台（DevilWEB 2.1 为例）。点击左侧Website list选项卡-Add new website按钮，选择 Node.js 项目，并在下方Basic configuration处填写域名（如果是自定域名则需在 DNS 服务商如 Cloudflare 做好解析）；Runtime 部分，Node executable 的 Node.js 版本按文档说明建议设置为22.Y.Z或24.Y.Z。完成后点击界面右下角Add new website按钮创建网站。

随后，在左侧Port reservation选项卡点击Reserve a new port增加一个端口，端口号自定（后面要用），如果不可用会提示。

之后回到Website list选项卡，查看是否已创建刚才的 Node.js 站点；通过 FTP 登入，检查/domains/【域名】/public_nodejs是否存在。现在尝试访问该域名，理应看到 Serv00 的 Node.js 站点默认页面。

现在，通过 FTP 工具将/domains/【域名】/public_nodejs目录下的文件删除，并将前面下载的发行版压缩包上传至该目录，解压（可以通过左侧的File manager选项卡进入在线文件管理器，依次找到压缩包，可以在线解压）。解压后文件相对位置大致如下：

增加启动文件

经过检查，得到几个信息：

源码要求
package.json:23根目录 .js 是 ESM，入口需要用 import（或动态 import()）
package.json:24；server/index.js:220项目自身入口是 server/index.js，但它只在自己是进程入口时才自动监听，被 app.js 导入后不会自动启动
server/index.js:35;64-68;96；server/http/boot.js:87;89项目提供了 API 启动方式，也就是说编写app.js只需转接，不需要重写逻辑
server/http/config.js:41端口可由启动函数传入，但opts.port 优先于环境变量 PORT

如此一来，app.js（通常情况下）只需要加入 require 与 listen 相关设置，在本项目中则是加载模块→runMain(startServer)。模板应用是 http.createServer().listen()，
本项目的 listen 已封装在 startServer() 内部（server/index.js:96 起），这意味着与其重写一遍不如转接项目提供的 API。这样既方便 Serv00 启动程序，又避免后续升级合并差异带来的不便。

试试静态 import 导入

由刚才的发现，我们自然地想到：

  • app.js 必须主动调用启动函数，而不是自己写 listen()。项目的监听行为在 startServer() 中，app.js 负责改变调用时机；
  • startServer 与 runMain 都是现成导出，两个 import 就是模板里 require 的 ESM 对应物，
    runMain(startServer) 是模板里 listen() 的对应物；
  • boot.js 开头的注释表明 runMain 附带的
    进程级行为，正是 npm start 执行的同一段代码，只需一行即可让服务器上获得与本地完全一致的启动体验，因此我们选 runMain(startServer) 而非裸调 startServer()，；
  • 端口交给环境变量，因为宿主面板会注入 PORT，app.js 不必关心端口（这条是我猜的）。

那么固定端口试试

再次研究发现 Serv00 面板无法设置环境变量，之前猜想的依赖 PORT/HOST 注入机制不起作用（我印象中 Serv00 是可以设置变量的，但比较麻烦），综合考虑，决定将端口写进启动文件；而且 startServer({ port: PORT }) 能覆盖环境变量，不改动既有代码；

由 boot.js:87 可知 runMain 的签名要求传启动函数而非启动结果；

端口值按 Serv00 实际设定情况调整（事后发现 Node.js 类型下这个常量根本不生效但无害；后来用 SSH 登入后使用 sockstat 确认没有进程占用目标端口）。

不应该啊……排查一下：

Serv00 会把应用的错误写入 domains/<DOMAIN>/logs/error.log：

经过我的观察，访客每访问一次，日志中就有这样的内容：

动态 import

检查 error.log 时注意到其中反复出现 ERR_REQUIRE_ASYNC_MODULE，并得知 Serv00 的 Node.js 类型页由 Phusion Passenger 框架的 node-loader.js 调用 app.js 处理。

Node 的规则是：require() 进入 ESM 时会同步求值入口及其全部静态 import 内容，其中任一模块含顶层 await（Top-Level Await，简称 TLA）即整体失败；而本项目 TLA 位于 server/sim/simdata.js:509，与 server/sim/content/kits/index.js:172 属既有代码，我不作修改。

这样一来，此时虽然 Node.js≥22.12 版本允许 require() 加载 ESM，但禁止其静态依赖含 TLA，故而报
ERR_REQUIRE_ASYNC_MODULE，于是启动失败，Apache 报 500。测试了一下，找到对应的文件：

然后搜索了许多文档还发现 Serv00 的 Node.js 环境由 Phusion Passenger 接管监听，而不是走 proxy 的方案，因此 Node.js 类型是不需要端口环境变量的。

在麻烦 DeepSeek 和 Mimo 亲自登入 SSH 智斗了一段时间后，我得到了一个解决方法：

思路大致如下：

  • require() 同步加载 app.js 时，同步求值路径上只有 app.js 自身；不再使用静态 import，改由动态 import() 异步拉起。由于动态导入不属于 require() 的同步图，因此避免了 TLA 限制，且启动流程不变；
  • process.exit(1) 对齐 runMain 启动失败即退出码 1 的既有行为（boot.js:99-101），避免宿主侧出现进程活着但永远不响应的情况；
  • 保留 PORT，将来改用 proxy 反代方式时它会恢复作用，方便日后兼容；

启动与更新

通过这种方法部署的 Node.js 类型项目无需手动启动命令，首次 HTTP 访问即可拉起应用，较长时间闲置后冷启动速度约 8 秒；curl 检查域名也是通的，WebSocket 也正常跑起来了（测试时加了 --http1.1 参数才得到真实的 101 反馈）；用 sockstat -l \| grep 8180 再次确认该端口没有被监听而是被接管了。

那么我们在浏览器中进行一个域名的访问：

  • https://game.example.com
  • https://game.example.com/healthz
